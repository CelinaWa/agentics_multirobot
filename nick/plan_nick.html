What RAX already does, and what the coordinator adds

Plan for branch nick. Goal: several robots working together from one high-level instruction such as "clean the house". Three stages: task decomposition (this plan), orchestration, self-improvement. Nothing here is built yet.

Approach

The decomposer runs as an ordinary RAX session with a new role, "coordinator". RAX already starts a sandboxed Claude agent with instructions, tools, memory, a skill library and a channel to a human. The coordinator reuses all of that. The decomposition logic is written in Markdown; the only new Python is a small set of read-only tools.

"Skill" on this page means a robot behaviour for one subtask: a controller RAX built into a robot's skill library, or a trained policy. A single-robot skill belongs to one robot name, a multi-robot skill to several.

Nothing is fixed to two or three robots, or to the robot types in the repo today. The fleet file lists any number of robots, and a multi-robot task names as many as it needs. RAX has no single file describing what each robot can do, so each robot type gets one small capability card, robots/<type>.json, with free-form capability tags. Adding a robot type means adding a card, with no code change; one individual robot can override tags in the fleet file.

read goal→look up fleet and trained skills→propose task tree→split until each leaf is one skill→check→repair→second opinion→ask human if unclear→submit plan

Three stages and what each one lets you test

StageDeliversTestable when done
1 · nowDecomposition. Goal in, plan out: essential subtasks, robots assigned, trained skills reused, task files for skills still to build.
  • Three example goals, each run three times, every run passes the fixed checks and that goal's expectations
  • Registering a new trained skill changes the next plan to use it
  • An emitted task file starts a normal RAX session
No robot needed.
2 · laterOrchestration. The coordinator starts robot sessions from the plan, watches them, answers their requests, switches tasks and replans.
  • 2.1, no robots: a plan runs end to end against fake skills; order follows dependencies; independent tasks run at once on different robots; an injected failure causes a retry, a switch to another robot, or a replan
  • 2.2, simulation: one plan drives a G1 session and an R1 session to completion
  • 2.3, real robots with your collaborator's skills
3 · lastSelf-improvement. Failures traced to a bad split or assignment become lessons the coordinator applies next time.
  • 3.1: replay a logged failure; rerunning the same goal no longer repeats the mistake
  • 3.2: the stage 1 expectations are scored before and after learning; no goal gets worse

The plan it outputs

One entry per subtask. This is the contract your collaborator's training and the later orchestration stage read. Illustrative values.

{
  "id": "t3",
  "title": "Carry the bench to the hallway",
  "parent": "t1",              "depends_on": ["t2"],
  "kind": "multi",             "robots": ["g1-a", "r1-a"],
  "assignment_reason": "too long for one robot; both are in the living room",
  "alternatives": [["g1-a", "rby1-a"]],
  "required_capabilities": ["walk_while_holding", "two_hand_grip"],
  "skill": {"status": "to_build"},
  "preconditions": ["bench is clear of objects"],
  "success_condition": "bench stands in the hallway, both robots standing, hands open",
  "resources": ["bench", "living-room doorway"],
  "on_failure": "set the bench down, ask the operator"
}

When a trained skill exists, skill names it instead, with where it came from, its status and its recorded success counts. A trained multi-robot policy is registered with the header RAX skills already use, plus one line:

skill-library/multi/skills/bench-carry-2/SKILL.md
---
name: bench-carry-2
description: two robots lift a bench by its ends and carry it up to 3 m
status: verified
robot: multi
robots: [g1sonic, r1sonic]     # the one added line
entry: code/run.py
---
evidence/runs.jsonl            one line per run: success or failure, unattended or not
