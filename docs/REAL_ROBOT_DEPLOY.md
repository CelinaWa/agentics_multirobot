# 真机部署流程（人话版）

> 这份是给人看的版本。每个数值、文件名、参数的出处在同目录的 `REAL_ROBOT_DEPLOY_technical.md`。
> 写于 2026-10-26，依据 `2/homebody/.cache/rax-g1real` 里的代码和 `3/eng` 的 sim 实验。

---

## 一、先搞清楚有哪几个"角色"

把整套系统想成四个人在合作：

| 角色 | 它是什么 | 类比 |
|---|---|---|
| **SONIC 控制器**（deploy stack） | NVIDIA 的一个程序，跑在机器人旁边的电脑上，每秒 50 次算电机该怎么转，负责让 G1 不摔倒。它是"冻住"的，我们不改它 | 机器人的**小脑**：你告诉它想摆什么姿势，它负责平衡 |
| **robot service**（RAX 的 g1sonic backend） | 我们这边唯一能跟 SONIC 说话的程序。它接收 agent 的指令，先做安检（关节是否超限、动作是不是太猛、机器人是不是在倒），再发给 SONIC | **翻译官 + 安检员**：所有命令必须过它这一关 |
| **Claude agent** | Claude Code 跑在一个沙箱里，只能通过几个"工具"（看一眼、动手臂、走几步、握手）去指挥机器人，碰不到任何别的东西 | **操作手**：它只会按工具按钮，摸不到电机 |
| **你（operator）** | 站在急停旁边的人。你不"上钥匙"（arm），机器人一步也不动；你拔钥匙（disarm），它当场停住保持姿势 | **拿钥匙的人** |

另外还有两个硬件：**吊架**（gantry，开机时吊着机器人）和**头上的相机**（跑在 G1 自带的 Jetson 上，IP 192.168.123.164，给 agent 提供彩色图 + 深度）。

数据怎么流：agent 按工具 → robot service 安检 → 用 ZMQ 发给 SONIC（端口 5556 发姿势，5557 收状态）→ SONIC 用 DDS 驱动电机。agent 从头到尾看不到 DDS，也看不到 SONIC。

## 二、四道安全保险（从外到内）

1. **物理急停** + SONIC 自己的停止键（键盘 `O` 或手柄 Select）：所有关节瞬间"软掉"，机器人坐到地上。这是最后的底线，永远有效。
2. **钥匙（arming）**：一个文件 `operator/armed.json`，只有你能写。robot service 每一拍都看一眼：没钥匙 → 任何动作命令直接拒绝；动作中途拔钥匙 → 20 毫秒内停住，机器人保持当前姿势不动（注意是"定住"，不是"软掉"）。
3. **安检员的规矩**（robot service 自己卡的）：
   - 关节不能超过 URDF 限位（留 0.05 rad 余量）；
   - 相邻两拍之间关节最多变 0.15 rad，一个命令的第一拍离当前姿势最多 0.35 rad（防止猛抽一下）；
   - 每个动作命令最后 5 拍必须一样（动完要停在一个姿势上，不能"甩出去"）；
   - 状态数据超过 0.2 秒没更新 → 当作断线，拒绝动 / 中断当前动作；
   - **身体倾斜超过 60 度 → 自动叫 SONIC 软掉，并自动拔钥匙**。之后你得重新上钥匙它才肯再动。
4. **SONIC 自己的每拍自检**和电机限位。

## 三、开一次实验，按顺序做什么

### 开始前的硬件状态
机器人吊在吊架上，脚离地约 20 cm，电机已上电，SONIC 程序已启动但处于"等待"状态。**这时 SONIC 不往外发任何状态**，所以 agent 的 `g1_status` 会报"没有状态"，这是正常的。

### 步骤

1. **写配置**（不会动任何东西）：
   ```
   $RAX_PYTHON scripts/configure_session.py --task <任务名> --task-file task.md --robot g1sonic --backend-options <真机参数.json>
   ```
   它打印出一个 `<session>/operator-input.json`。

2. **启动 agent 和 robot service**：
   ```
   bash scripts/start_agent.sh --config <session>/operator-input.json
   ```
   同时可以开 dashboard（`scripts/run_dashboard.sh`）在浏览器里看钥匙状态、agent 的请求、相机画面、实时姿态。

3. **agent 开始读任务、读它的技能文档**，先调 `g1_status`。它想动就会被拒绝，并通过 `request_operator` 请你上钥匙。

4. **你上钥匙**：`rby1 arm 5`（5 分钟后自动失效；不写数字就一直有效），终端会让你输入 `ARM` 确认"有人在急停旁、周围已清空"。随时 `rby1 disarm` 拔掉。

5. **第一次 `g1_hold` 是整个流程最危险的一步：它会把 SONIC "点火"。** 具体过程：
   - robot service 给 SONIC 发"开始，用你自己的行走规划器模式"→ SONIC 开始控制，机器人**在吊架上原地站起来**；
   - 等至少 3 秒，再等到机器人"安静"（倾斜 < 10 度、关节都不怎么动，持续 1 秒）；最多等 15 秒，还不安静就报错放弃；
   - **按 `s` 之前就把吊架放下到脚承重（带子还轻轻托着），按完 `s` 几秒内把带子彻底放松到不受力，但别摘**。脚离地时 SONIC 没有地面反力，会在空中乱蹬（sim 里腿速 35 rad/s）；`s` 之后带子还拉着骨盆的话策略会对抗、上身起振；放早了，机器人会以半空中正在迈的那个怪姿势落地，可能慢慢倒；**摘带子的时机是第一次 `g1_walk` 走完之后**，而且摘之前确认两脚分开约一肩宽、机器人安静 2 秒以上（原因见"目前的鲁棒性"）。
   - 机器人安静后，robot service 记下它当时的姿势，把 SONIC 切到"听姿势指令"模式，然后用 1.5 秒慢慢过渡到标准站姿。一帧跳到标准站姿会把它掀翻（sim 里试过）。

6. **agent 开始干活**，它手里只有这几个按钮：
   | 工具 | 人话 |
   |---|---|
   | `g1_observe` | 拍一张彩色 + 深度图，附带相机位置、关节、身体朝向 |
   | `g1_pixel_to_position` | 点图上某个像素，告诉你那东西在机器人盆骨坐标系里的 xyz |
   | `g1_free_space_move` | "把左手/右手移到这个位置"，用 cuRobo 规划手臂（只避自己的身体，不知道桌子在哪）。可以先 preview 再 execute |
   | `g1_step` | 直接发 1 到 100 帧的全身姿势（最多 2 秒），最底层的控制 |
   | `g1_hand_shape` | 定义 Dex3 手"张开"和"握紧"分别长什么样 |
   | `g1_walk` | 走路：往前最多 3 米、转最多 ±45 度、速度 0.1 到 0.6 m/s。**只能往前走，不能后退、不能横移** |
   | `g1_hold` | 停下来保持当前姿势（不是急停） |

   agent 会自己写代码放在 `agent-workspace/code/` 里跑，总结出好用的套路存进技能库。

7. **agent 请你帮忙**（`request_operator`）：比如"把球放回桌上"、"机器人卡住了"。它会一直等到你 `rby1 reply "done"`，等的时候机器人保持姿势不动。

8. **结束**：先 `rby1 disarm`，再在 agent 终端 Ctrl-C。关 SONIC 前**先把吊架带子挂上**，再按 `O`（机器人会软掉坐下），然后断电。所有记录在 `<session>/mcp.jsonl`（每一次工具调用）和 `runtime/frames/`（每一张图）。

## 四、关于"走路"你需要知道的几件事

`g1_walk` 是把机器人交给 SONIC 自己的行走规划器，走完再接回来。robot service 在里面偷偷做了这些保护（都是 sim 里摔出来的教训）：

- **第一次走之前先左右各扭 15 度**热身。这些扭动是原地小碎步，从来没摔过；真正危险的是热身之后**第一次前进起步那一步**（约 5% 到 10% 会摔，见下面"目前的鲁棒性"），所以第一次 `g1_walk` 要在吊架带子还挂着的时候做。
- **超过 0.5 米的路拆成几段走**，每段单独启停。0.9 米一口气走，sim 里会摔或者跑飞。
- **转向速度压到 30 度/秒**。45 度/秒时腰以 7 rad/s 甩，摔了。
- **转弯时会顺带往前挪 10 到 20 cm**，不是原地转。刚走完就原地转（双脚前后错开 24 cm），摔了。所以转弯前要留出前方空间。
- **走完等 1.5 秒 + 最多 6 秒等它站稳**，再切回"听指令"模式。**如果它一直在原地踏步停不下来，robot service 就不切回去，让规划器继续替它平衡**。这时 agent 的 `g1_hold` 其实不起作用（这是我们在 sim 里发现的一个坑，后面第六节讲）。
- **走的距离是"命令值"不是"实测值"**，机器人没有里程计。sim 里我们用腿的关节角算了一个里程计（`3/eng/legodo.py`），只用关节数据，理论上真机能用，但没在真机验过。
- `carry=true` 时走路会把腰、双臂、双手冻住，不然规划器会甩手臂，手里的东西会掉。

## 五、出事了会怎样

| 出什么事 | 系统自动做什么 | 你要做什么 |
|---|---|---|
| 倾斜超过 60 度 | 叫 SONIC 软掉 + 自动拔钥匙，记一个"摔倒故障" | 扶住或让它坐下，重新挂回吊架，检查，重新 `rby1 arm`。新钥匙会清掉故障，下一次 `g1_hold` 重新走第三节第 5 步的点火流程 |
| 状态 0.2 秒没更新 | 拒绝新动作 / 中断正在做的动作，机器人在 SONIC 里保持最后姿势 | 看 SONIC 的终端和网线 |
| 状态 2 秒没更新 | 认为 SONIC 死了或重启了，忘掉之前的姿势，下次上钥匙后的 hold 重新点火 | 挂上吊架再重启 SONIC |
| 你拔钥匙 | 20 毫秒内停住，保持姿势 | 无 |
| 点火后 15 秒还不安静（吊得不平、靠着什么东西） | 点火失败，可以重试 | 把机器人摆正、清掉接触物，重新上钥匙 |
| 键盘 `O` / 手柄 Select / 急停 | 全身软掉，坐下 | 能的话先把吊架带子挂上 |

## 六、Sim 里跑的和真机到底差在哪

好消息：**sim 和真机用的是同一个 robot service、同一套工具、同一套安检规矩**。agent 或我们写的控制代码不用改。差的是周围的一切：

| | sim（`3/eng`，容器 `sonic-sim2sim`） | 真机 |
|---|---|---|
| 谁拿钥匙、谁放吊架 | **代码自己**：`trial.py` 直接写 `armed.json`，`gantry.py` 给仿真器发"放下/松开"按键 | **你**：手动 `rby1 arm`，手动放吊架，时机靠你把握 |
| SONIC 怎么启动 | `run_sim2sim.sh` 在 tmux 里拉起仿真器 + SONIC，走本机回环，关掉 CRC 校验，GPU 忙时还能把时间放慢 | 在机器人网络上按 NVIDIA / MA-Teleop 的方式启动，实时，不能放慢。参数里必须带 `--planner-file`，否则 ZMQ 点火会直接把它停掉；参考动作目录建议用"站立"动作而不是自带的 example 舞蹈（见第七节第一条，属于卫生措施，不是开机摔倒的解药） |
| 几个参数 | 状态允许 1.5 秒不更新、点火不额外等、时间比例 = 放慢倍数、相机在 127.0.0.1 | 状态 0.2 秒、点火至少等 3 秒、时间比例 1.0、相机在 Jetson 192.168.123.164 |
| 相机 | 仿真渲染，**深度图完美无噪声** | 真实深度相机：盘子边缘、反光表面有洞有噪声；相机装的位置和 URDF 不一样时要填 `camera_pose_override` |
| 真值（ground truth） | 有。能直接读仿真器里盘子、手、盆骨的真实位置，自动判成功、自动分析摔倒原因 | **没有**。成功靠相机或靠人眼判断，摔倒靠人看。我们的控制代码本来就没用真值（真值只用来打分），所以代码能搬，打分方法搬不了 |
| 摔了怎么办 | 脚本自动重启仿真器，机器人重新吊回空中，实验接着跑 | **摔了就是摔坏**。系统只会软掉 + 拔钥匙，剩下的靠人。sim 里每一次摔倒在真机上都是一次事故 |
| 开机 | 全自动，每次实验都是新的仿真器 | 手动放吊架，第三节第 5 步 |
| 走路标定 | `ctl.py` 里"命令 X 米实际走 Y 米"的表是在 sim 里用真值量的 | **必须在真机重新量**（卷尺）。地面摩擦、电池电量、实时性都会改变这张表 |
| 转向安全阈值 | 用 sim 的倾斜统计调的（正常转 3 到 5 度，摔前的那一转 9 到 14 度） | 代码一样，但阈值要拿真机 IMU 数据重新看 |
| 抓取 | MuJoCo 接触仿真，盘子捏边成功率目前 5/85 | Dex3 手的柔性、真盘子的重量和摩擦都不一样；抓取成败会变，但"怎么摔"的机制一样 |
| 谁在控制 | 工程实验里是 Python 脚本直接按工具（没有大模型） | Claude Code 在沙箱里按工具，4 小时一个 session |

**只存在于 sim、真机上没有的东西**：真值数据流、给仿真器的按键（放带子/松开/渐变）、时间放慢、完美深度、自动重启、物体自动归位。

## 七、目前 sim 里的鲁棒性现状（给你判断"敢不敢上真机"）

你的标准：任务失败可以接受，摔倒和失控不行。

- **开机是最大的摔倒来源，今天拆成了两类（见 FAILURE_LOG 169 到 171 行）**。全部 1132 次开机里 94 次摔倒。**第一类：第一次前进走路起步那一步（约每 10 到 20 次开机摔 1 次）**。逐帧回放加 SONIC 内部状态记录证明：planner 规划的起步轨迹在摔和不摔的开机里一模一样，是**策略本身**偶尔迈不好第一步（摆动腿的膝盖超过目标、该落地时脚还在空中，机器人前倾 1 秒内从 10 度到 60 度）。和参考动作无关（换成只有站立的参考目录没变化），和起步速度关系不大（0.2 m/s 起步、速度渐变都照样摔，而且渐变让 0.2 米的短路程根本走不动）；站姿不对称（右膝多弯、左脚在前）会提高摔的概率，但完全对称的站姿也摔过，所以靠检查站姿再起步**治不了**。真正安全的只有一个事实：**原地小碎步（转身用的那种，0.1 m/s）从来没摔过，571 次转身 0 摔；只有第一次"真正迈步"危险，之后的走路基本不摔**。所以真机上的做法是：**第一次 `g1_walk`（含它自带的热身转身和第一段前进）必须在吊架带子还挂着的时候做完**，走完再摘带子。**第二类：松开吊架之后站着站着倒了（约 1/30）**。吊着的时候机器人会在带子里"原地踏步"十几秒（带子托着它，脚不承重），踏完有时两脚并得很拢（脚间距 13 到 16 厘米，正常 26 厘米），带子松开后 2 到 3 秒它就往前倒。**真机上松带子之前看一眼两脚间距：两脚要分开约一肩宽、机器人安静 2 秒以上再松；脚并拢了就别松，重新吊起来让它再站一次**。今天下午一组 40 次开机的对照数据：29 次干净；4 次第一步摔（或险些摔）；3 次松带子后 2 秒倒；4 次从带子上下来时就站歪了（两脚前后错开 15 厘米以上、身体歪 10 度），之后怎么扭都站不稳，强行走就摔。所以**松带子前先看站姿**这条真机规则同时管住了后面两类。站立参考目录保留（无副作用），真机上也建议用它，但它不是开机摔倒的解药。
- **连续转弯是任务中摔倒的主因**：最近 15 次任务中摔倒有 10 次是在连续 45 度转弯时或刚转完。现在加了保护（转弯拆成 30 度以内的小段、倾斜超过 8 度不许走、一段转完晃超过 12 度就停止后面的转弯），正在跑验证。
- **拉冰箱门摔过 3 次**。开门本身 10/10，开+关 8/10。还没试过把东西放进冰箱。
- **手臂作业基本不摔**：盘子抓取失败的时候机器人都是站着的（倾斜 2 到 3 度）。失败原因是够不着、身体往后慢慢滑（手臂伸出去前倾时每秒退 3 mm）、还有下面这个坑。
- **走完切不回来的坑**：走完后机器人有时一直原地踏步，这时 `g1_hold` 没效果，等的程序会卡一分钟。已加了补救（20 秒和 40 秒后再走 0.1 米让它重新站稳）。真机上这种情况就是"机器人一直原地踏步"，你直接拔钥匙就行，规划器会继续替它保持平衡。
- sim 里还有一类"仿真器重启导致的瘫倒"（76 次），真机上不存在这种事，但 SONIC 程序崩了的话机器人会软掉在地上。

## 八、建议真机第一天怎么做

全程机器人挂着吊架（带子可以放松但别摘），一层一层来：

1. SONIC 启动、机器人吊着：先 `g1_status`（什么都不会动，预期报"没有状态"），再在**没上钥匙**的情况下试一个 `g1_step`，必须被拒绝。
2. `rby1 arm 5`，`g1_hold`：看机器人在吊架上站起来，在等待窗口里放下、松带子，确认 `g1_status` 显示"streamed"模式、倾斜 < 2 度、没有故障。**把这一步重复做好几遍**再往下走，这是 sim 里记录最差的一步。
3. 一个小动作的 `g1_step`（抬手臂，1 秒缓动，末尾停住），看关节跟踪误差，sim 里是 0.11 到 0.12 rad。
4. `g1_observe` + `g1_pixel_to_position` 对一个已知位置的物体，拿尺子量一下算出来的位置准不准。相机安装位置和深度噪声是和 sim 差别最大的地方。
5. 只做走路热身（转 15 度、转 -15 度），然后往前走 0.3 米，量实际走了多少，重建 `ctl.py` 的走路标定表。
6. 这些都没问题了再做任务。先做只用手臂的（桌边捏盘子），**冰箱门和多次转弯的导航放最后**。
